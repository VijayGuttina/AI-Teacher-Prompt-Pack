# Primary Computing Framework

## Purpose

This module defines a compact, reusable workflow library for primary teachers using AI to plan, teach, assess and adapt Computing. Workflows are designed around genuine teacher jobs rather than isolated prompt ideas.

## Workflow architecture

The Computing library is organised into 10 workflow families, with 10 workflows in each family: 100 workflows in total.

1. Computer systems and digital devices
2. Networks and connectivity
3. Programming and computational thinking
4. Data and information
5. Creating digital content
6. Online safety and responsible use
7. Digital literacy and productivity
8. Algorithms, decomposition and problem solving
9. Vocabulary, explanation and misconceptions
10. Assessment, diagnosis and intervention

## Core principles

- Preserve the Computing construct when adapting tasks.
- Distinguish computing knowledge from generic ICT/productivity skills.
- Do not invent software features, interfaces, device capabilities or network conditions.
- Code must be syntactically plausible and age-appropriate; where execution matters, recommend testing in the stated environment.
- Never imply that generated code has been executed unless execution evidence is actually available.
- Use supplied pupil code, outputs and evidence when diagnosing misconceptions.
- Do not expose pupils to unsafe, inappropriate or unnecessary online content.
- Treat privacy, passwords, personal data and account security as genuine safety considerations.
- Avoid presenting rapidly changing product/interface details as timeless facts.
- Adapt accessibility without unnecessarily reducing computational thinking or problem-solving demand.

## Standard workflow structure

Every workflow should use the established library structure:

**ROLE → CONTEXT → TASK → REQUIREMENTS → OUTPUT FORMAT → QUALITY CHECKS → OPTIONAL CUSTOMISATION**

## Verification model

Structural QA is separate from execution verification. A workflow is only individually verified when it has been executed and assessed with the stated model, input, output judgement and reviewer notes. Representative testing can establish confidence in workflow families but must not be represented as individual verification of every workflow.

## Primary Computing quality gates

Every generated result should be checked for:

1. Technical accuracy
2. Age and curriculum appropriateness
3. Computational thinking demand
4. Code/environment assumptions
5. Data and privacy safety
6. Online-safety implications
7. Accessibility and inclusion
8. Evidence-based diagnosis
9. Clear teacher usability
10. Appropriate qualification where technology changes rapidly

## Planned verification

The subject will follow the standard library sequence:

**Framework → workflows → verification metadata → worked examples → representative execution tests → targeted spot checks → freeze.**
